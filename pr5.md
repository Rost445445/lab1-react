# Звіт з Практичної роботи №5: Побудова ієрархії компонентів

## 1. Проектування структури (Smart vs Dumb)

**Різниця на прикладі профілю:**
- **Smart (Контейнерні):** `ProfilePage`. Він відповідає за логіку: отримання даних користувача з API або контексту, керування станом завантаження та передачу даних вниз. Він не містить складних стилів, а лише координує інші компоненти.
- **Dumb (Презентаційні):** `Sidebar`, `UserInfo`, `ActivityItem`. Вони отримують готові дані через пропси і просто відображають їх. Вони не знають, звідки взялися дані, і легко перевикористовуються в іншому місці.

**Ієрархія компонентів:**
- `ProfilePage` (Smart)
  - `Sidebar` (Dumb)
  - `MainContent` (Composition)
    - `UserInfo` (Dumb)
    - `ActivityList` (List)
      - `ActivityItem` (Atom)

## 2. Декомпозиція картки товару (у 3 рівні)

У коді `src/components/product/ProductComponents.jsx` реалізовано наступну ієрархію:
- **Level 1 (ProductCard):** Контейнер, що зберігає стан `quantity`.
- **Level 2 (ProductDetails, ProductActions):** Композиційні компоненти. `ProductActions` отримує `quantity` та функції зміни стану.
- **Level 3 (StarRating, UIButton):** Атомарні компоненти, що відповідають за візуальні елементи.

## 3. Робота з React Developer Tools

**Дерево в DevTools:**
У вкладці "Components" ми побачимо деревовидну структуру:
`ProductCard`
  └─ `ProductDetails`
       └─ `StarRating`
  └─ `ProductActions`
       └─ `UIButton` (Мінус)
       └─ `UIButton` (Плюс)
       └─ `UIButton` (В кошик)

**Джерело істини (Single Source of Truth):**
Для стану кількості товару (`quantity`) джерелом істини є компонент `ProductCard`. Стан піднятий саме сюди, оскільки він потрібен був би (в реальному додатку) і для відображення в деталях, і для передачі при натисканні "В кошик".

## 4. Контрольні запитання

### Чому важливо відокремлювати логіку від відображення?
Це покращує **тестованість** (презентаційні компоненти легше тестувати візуально через Storybook) та **перевикористанність** (ви можете змінити дизайн картки, не чіпаючи логіку розрахунків).

### Що таке "Prop Drilling" та як з ним боротися?
Це передача пропсів через проміжні компоненти, яким ці дані не потрібні. **Способи боротьби:** Context API, Redux/Zustand, або використання Composition (`children`).

### Чому .map() краще розміщувати в проміжних спискових компонентах?
Це робить головний контейнер простішим і легшим для читання. Компонент-список (наприклад, `ActivityList`) інкапсулює логіку ітерації та передачу ключів (`key`), що спрощує структурування інтерфейсу.

### Як props.children допомагає у створенні гнучких компонентів?
`Props.children` дозволяє створювати компоненти-"обгортки" (Layouts, Modals, Cards), які відповідають лише за структуру та стилі оформлення, дозволяючи вставляти в себе будь-який контент. Це робить компоненти максимально гнучкими.

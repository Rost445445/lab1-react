# Звіт з Лабораторної роботи №5: Система автентифікації та захищені маршрути

## 1. Реалізація AuthContext

Дані про користувача та функції керування сесією передаються через `AuthContext.Provider`. Це дозволяє будь-якому компоненту в дереві отримати доступ до стану авторизації.

```javascript
// src/context/AuthContext.jsx
export const AuthProvider = ({ children }) => {
  const [user, setUser] = useState(null);

  const login = (userData) => {
    setUser(userData);
    localStorage.setItem('user', JSON.stringify(userData));
  };

  const logout = () => {
    setUser(null);
    localStorage.removeItem('user');
  };

  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
};
```

## 2. Логіка ProtectedRoute

Компонент `ProtectedRoute` працює як "шлюз" для приватних сторінок. Він використовує хук `useAuth` для перевірки наявності об'єкта `user`. 
- Якщо `user === null`, компонент повертає `<Navigate to="/login" replace />`, що миттєво перенаправляє користувача на сторінку входу.
- Якщо користувач авторизований, компонент рендерить `children` (вкладені компоненти, наприклад, сторінку профілю).

## 3. Відповіді на контрольні запитання

### Яку архітектурну проблему вирішує використання Context API?
Context API вирішує проблему **Prop Drilling** — необхідність передавати пропси через багато рівнів компонентів, які самі ці дані не використовують, а лише передають їх далі своїм нащадкам.

### Чому для складних додатків обирають Redux або Zustand?
Context API не оптимізований для частих оновлень великої кількості незалежних даних: при зміні одного значення у Context, перерендериться все дерево споживачів. **Redux** та **Zustand** мають кращі механізми селекторів (оновлюють тільки ті компоненти, які реально використовують змінену частину стану) та потужні інструменти для дебагу (DevTools).

### Яка роль патерна Higher-Order Component (HOC) при реалізації захищених маршрутів?
HOC (яким є `ProtectedRoute`) дозволяє відокремити бізнес-логіку сторінки від логіки перевірки прав доступу. Це робить код чистішим і дозволяє легко "захистити" будь-який маршрут, просто обгорнувши його в цей компонент.

### Чому використовується replace: true при перенаправленні?
Властивість `replace: true` замінює поточний запис у стеку історії браузера замість того, щоб додавати новий. 
**Вплив на історію:** Це важливо, щоб після перенаправлення на сторінку входу користувач не міг натиснути кнопку "Назад" у браузері і знову потрапити на захищену сторінку, з якої його щойно вигнало (що створило б нескінченний цикл редиректів).

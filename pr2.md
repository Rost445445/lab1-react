# Звіт з Практичної роботи №2: Трансформація масивів даних у React

## Частина 4: Контрольні запитання

### 1. Чому при рендерингу масивів обов'язково використовувати атрибут key і що станеться, якщо його не вказати?
Атрибут `key` потрібен React для ідентифікації елементів у списку під час оновлення (Reconciliation). Ключ дозволяє React зрозуміти, які саме елементи змінилися, додалися або були видалені, замість того, щоб перемальовувати весь список з нуля.
**Якщо не вказати key:**
- В консолі розробника з'явиться попередження: `Warning: Each child in a list should have a unique "key" prop.`
- Погіршиться продуктивність (React буде частіше робити повний ре-рендер DOM).
- Можуть виникнути непередбачувані помилки зі станом локальних компонентів (наприклад, фокус в інпутах або анімації можуть "прикріпитися" не до того елемента).

### 2. У чому різниця між .map() та .forEach()? Чому .forEach() не підходить для JSX?
- `.map()` повертає **новий масив**, отриманий шляхом трансформації кожного елемента. Це дозволяє React отримати масив JSX-елементів, який він може відразу відрендерити.
- `.forEach()` просто виконує функцію для кожного елемента, але **повертає undefined**.
**Чому `.forEach()` не підходить для JSX:** Оскільки React очікує, що вираз у `{}` поверне щось, що можна відобразити (наприклад, масив, число чи рядок), а `.forEach()` не повертає нічого, список просто не з'явиться на екрані.

### 3. Чому не рекомендується використовувати індекс масиву як key, якщо список може сортуватися або фільтруватися?
Ключ має бути стабільною та унікальною ознакою елемента даних. Індекс масиву залежить лише від позиції елемента. Якщо ми відсортуємо список, дані змінять свою позицію, а отже і свій індекс. React подумає, що на першій позиції залишився той самий елемент, хоча там тепер зовсім інші дані. Це призводить до серйозних багів, де внутрішній стан (state) старого елемента застосовується до нових даних.

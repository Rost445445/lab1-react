# Звіт з Лабораторної роботи №3

## Тема: Інтеграція системи фільтрації та пошуку в React

### 1. Фрагмент коду з логікою пошуку та фільтрації (App.jsx)
```jsx
const filteredPosts = posts.filter(post => {
  // Пошук за текстом (автор або вміст)
  const matchesSearch = post.author.toLowerCase().includes(searchTerm.toLowerCase()) || 
                        post.content.toLowerCase().includes(searchTerm.toLowerCase());
  
  // Фільтрація за категорією
  const matchesCategory = selectedCategory === 'All' || post.category === selectedCategory;
  
  // Комбінована логіка
  return matchesSearch && matchesCategory;
});
```

### 2. Пояснення щодо Empty State (Порожній стан)
В коді реалізована перевірка довжини відфільтрованого масиву `filteredPosts.length`. Якщо масив порожній (нічого не відповідає запиту), замість списку постів рендериться спеціальний блок `div` із класом `empty-state`, який виводить повідомлення: *"Нічого не знайдено за вашим запитом 😕"*. Це покращує UX, даючи зрозуміти користувачеві, що пошук спрацював, але результатів немає.

## Відповіді на контрольні запитання

### 1. Що таке "підняття стану" (lifting state up) і чому ми використали його для SearchBar?
**Підняття стану** — це патерн у React, коли стан переноситься з дочірнього компонента до найближчого спільного предка.
Ми використали його для `SearchBar`, тому що сам компонент пошуку не повинен знати, *як* фільтрувати дані. Його завдання — лише отримати ввід користувача. Дані (`posts`) знаходяться в `App.jsx`, тому саме там має зберігатися `searchTerm`, щоб на основі нього обчислювати `filteredPosts`.

### 2. Поясни асинхронну природу оновлення стану в useState.
Коли ми викликаємо `setSearchTerm`, React не оновлює змінну `searchTerm` миттєво. Замість цього він ставить оновлення в чергу і планує наступний рендер компонента. Це робиться для оптимізації продуктивності (batching). Значення стану в коді функції зміниться лише під час наступного виконання цієї функції (наступного рендера).

### 3. Чому для фільтрації ми створюємо нову змінну filteredPosts, а не змінюємо оригінальний масив posts у стані?
У React стан має бути незмінним (**immutable**). Якщо ми змінимо оригінальний масив, ми втратимо початкові дані назавжди і не зможемо "скинути" фільтр. Створення нової змінної (derivative state) під час кожного рендера — це чистий та безпечний підхід, який гарантує, що оригінальне джерело даних залишається цілісним.

### 4. У чому перевага керованих компонентів над некерованими при реалізації пошуку?
- **Синхронізація:** Стан React завжди є "єдиним джерелом істини".
- **Валідація та трансформація:** Ми можемо миттєво змінювати ввід (наприклад, перетворювати на верхній регістр) або забороняти певні символи.
- **Миттєвий відгук:** Пошук може відбуватися відразу під час друку (on the fly), без необхідності натискати "Submit".
- **Легкість тестування:** Простіше керувати поведінкою через пропси та стан.
